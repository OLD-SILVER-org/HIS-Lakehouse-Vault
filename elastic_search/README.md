# 🔍 Elasticsearch & Kibana Stack

This directory contains the Docker Compose setup for **Elasticsearch** and **Kibana**, used for log analysis, search, and data visualization within the HIS-Lakehouse platform.

## 🚀 How to Run

To start the **Elasticsearch & Kibana** stack, run:

```bash
docker compose --env-file .env up -d
```

To start the **Spark for Elasticsearch** stack (dedicated cluster), run:

```bash
cd src/spark
docker compose --env-file ../../.env up -d
```

### ⚙️ Configuration
The stack uses environment variables defined in the `.env` file:
- `ELASTIC_IMAGE`: Version of Elasticsearch (e.g., `8.17.2`).
- `KIBANA_IMAGE`: Version of Kibana.
- `ES_PASSWORD`: The password for the `elastic` user.

## 📌 Choosing the Document ID Column (Elasticsearch `_id`): Business Key vs RDBMS ID

When designing data synchronization pipelines to Elasticsearch, a crucial question arises: **Which column should be chosen as the identifier (`_id`) for a Document in ES?**

Below is a detailed comparison between **RDBMS IDs (Auto-increment ID / UUID)** and **Business Keys**:

### 1. Detailed Comparison

| Criterion | RDBMS ID (`id` column Auto-increment/UUID) | Business Key (e.g., `ma_nb`, `ma_benh_an`, `code_dichvu`) |
| :--- | :--- | :--- |
| **Characteristics** | Auto-incrementing numeric ID (1, 2, 3...) or random string (UUID) generated by the database. | Identifier generated by the business system (HIS), carrying real-world meaning. |
| **Advantages** | - Simple, guaranteed 100% unique in the source table.<br>- Not dependent on changes in business logic. | - **Ensures Idempotency (Safe for Upsert)**: No data duplication regardless of how many times synchronization is run.<br>- **Environment Independence**: Convenient for backup/restore or synchronization from multiple branches/environments where RDBMS IDs might change or conflict.<br>- **Blazing Fast Direct GET Queries (O(1))**: Retrieve document information directly via API using the business key without needing to execute a search query. |
| **Disadvantages** | - Prone to data duplication in ES if the target database in a different environment re-assigns IDs.<br>- Difficult to perform Direct GET on ES if the client only has the business key. | - Requires the business key to always exist (NOT NULL) and be unique in practice.<br>- If the business key changes (very rare), the old record on ES must be deleted. |

---

### 🏆 Recommendation & Best Practice

We **recommend using the Business Key** as the identifier (`_id`) in Elasticsearch for the following reasons:

1. **Idempotency**: When running Spark Batch or continuously listening to a Kafka stream, using a Business Key ensures that ES will automatically **Upsert (overwrite and update)** instead of creating duplicate, redundant documents.
2. **Multi-branch Scalability**: In large HIS systems, databases from different hospitals/branches often have overlapping auto-incrementing IDs (e.g., both Branch A and B might have a patient with `id = 100`). If RDBMS `id` is used, data will overwrite each other in a shared ES cluster. If `ma_nb` (e.g., `BN_A_100` and `BN_B_100`) is used, the data remains completely isolated and safe.
3. **API Optimization**: Frontend clients or other microservices needing detailed information about a service or patient can simply call:
   ```http
   GET /idx_benh_nhan/_doc/BN20260001
   ```
   This command returns results immediately, typically under **1ms**, and completely bypasses the ES search parser step.

---

### 🛠️ Practical Application in the Project

Based on the above recommendations, the identifier keys in the project's pipelines are mapped as follows:

1. **Patients (`idx_benh_nhan`)**: Uses **`ma_nb`** (Business Patient Code) instead of `nb_thong_tin_id`.
2. **Service Catalog (`idx_dich_vu`)**: Uses **`code_dichvu`** (Business Service Code) instead of `id`.
3. **Treatment Episodes (`idx_dot_dieu_tri`)**: Uses **`ma_benh_an`** (Business Medical Record Code) instead of `id`.
4. **Staff (`idx_nhan_vien`)**: Uses **`code_nhan_vien`** (Staff Code) instead of `id`.
